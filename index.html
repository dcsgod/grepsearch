I Built a RAG System
Without a Vector Database

GrepSearch replaces Pinecone and pgvector with BM25, a cross-encoder, and a 50-year-old Unix command — and it's faster, cheaper, and more accurate for most real-world workloads.

By dcsgod · May 2026 · github.com/dcsgod/grepsearch

The Problem With Pure Vector RAG

There's a quiet assumption baked into almost every RAG tutorial written in the last two years: you need a vector database. Chunk your documents, embed them with OpenAI or Cohere, push the vectors into Pinecone or Weaviate or pgvector, and query by cosine similarity.

I started questioning it when I noticed that two of the most highly regarded coding tools in the world — Cursor and Claude Code — don't use cloud vector databases to search your local codebase. They use grep. And they're fast.

Before diving into the solution, it's worth being precise about where standard vector search actually fails — because the failure modes aren't obvious until you hit them in production.

Memory bloat. A corpus of one million document chunks embedded as 1536-dimensional float32 vectors (OpenAI's text-embedding-3-small) consumes roughly 6 GB of RAM before metadata. For smaller teams, it's a heavy burden for what is fundamentally a search problem.

The exact-match problem. This is the one that surprises people. Semantic embeddings are extraordinarily good at capturing conceptual similarity, but notoriously unreliable for exact-match queries. If a developer asks "show me all calls to update_user_profile()," a vector search may return conceptually related functions while completely missing chunks that literally contain that function name.

The best coding tools in the world don't search your codebase with vectors. They use grep — and they combine it with something smarter.

The Architecture: Two-Stage Retrieval

The central insight is a separation of concerns that information retrieval researchers have known about for decades: split search into a fast, high-recall candidate generation phase, and a slow, high-precision reranking phase.

Query Expansion (Optional)
"car" → ["car", "automobile", "vehicle"]
WordNet offline · LLM via Ollama/OpenAI · ~1ms
Stage 1 — BM25 Lexical Search
Cast a wide net. Returns 100 candidates.
~1–5ms · High recall · Zero neural compute
Stage 2 — Cross-Encoder Reranking
(query, doc) → relevance score 0–1. Returns top 5.
~20–80ms · High precision · BERT-based
Final Results → LLM Prompt
Top 5 semantically verified chunks, ready for generation.
Total latency: typically under 100ms on CPU

You cast a wide, cheap net in Stage 1, then apply expensive semantic intelligence only to what the net catches. The Cross-Encoder never touches 99.9% of your corpus — because it doesn't need to.

Five Lines to Get Started

from greprag import GrepRAG, PipelineConfig

rag = GrepRAG(PipelineConfig(use_query_expansion=True))
rag.index_text(open("my_docs.txt").read(), source="my_docs.txt")

results = rag.search("how do transformers handle long sequences?")
for r in results:
    print(f"[{r.rank}] score={r.rerank_score:.3f} — {r.chunk.text[:80]}")

That's the entire public API for the majority of use cases. Now let's look at what's happening underneath.

Module Deep-Dive: The Lexical Layer

lexical.py implements two retrieval backends behind a shared interface. The primary one is BM25Retriever, backed by rank_bm25.BM25Okapi.

BM25 (Best Match 25) is a probabilistic ranking function that has been the backbone of search engines for decades — a smarter version of TF-IDF with built-in document-length normalization. The tokenizer lowercases text, strips punctuation, and removes a curated stopword list. Critically, the same tokenizer runs at index time and at query time.

# Stage 1 in isolation
retriever = BM25Retriever()
retriever.index(chunks)
candidates = retriever.search("attention mechanism", top_k=100)

# Multi-query fusion (after expansion) — uses Reciprocal Rank Fusion
candidates = retriever.search_multi(
    ["attention", "self-attention", "transformer attention"],
    top_k=100,
    fusion="rrf"  # Reciprocal Rank Fusion
)

When query expansion is active, the pipeline issues multiple BM25 queries. Reciprocal Rank Fusion (RRF) handles the merging: each document gets a score of 1 / (k + rank) from each list it appears in, summed across lists. Documents near the top of multiple lists are strongly promoted.

GrepRetriever — for File-Based Corpora

For large local codebases or document collections where loading everything into RAM isn't practical, GrepRetriever runs grep or ripgrep as a subprocess — scanning files on disk without loading them into memory at all.

results = rag.search_files(
    root="./my_project",
    query="how does the auth middleware work",
    file_patterns=["*.py", "*.md"],
    use_ripgrep=True,  # prefers rg if available
)
# No prior indexing needed — grep scans on-the-fly

The retriever includes a pure-Python fallback that walks the file tree if neither grep nor rg is available. Context lines around each match are configurable via context_lines.

Module Deep-Dive: The Cross-Encoder

Stage 2 is where semantic intelligence enters. CrossEncoderReranker wraps sentence_transformers.CrossEncoder with lazy model loading, batching, and graceful fallback.

Cross-Encoder vs Bi-Encoder

The standard way to add semantics to a RAG pipeline is with a bi-encoder: encode query and document independently, then compute cosine similarity. This is what OpenAI's embedding API gives you — and it scales to millions of documents because you can pre-compute every vector.

A cross-encoder feeds query and document together — concatenated into a single input — to a transformer model. The model attends across both texts simultaneously and outputs a scalar relevance score. This joint processing catches things a bi-encoder cannot: when a specific phrase in the query is directly addressed by a specific sentence in the document, or when the document contradicts the query's premise.

Why this works Cross-encoders are far too expensive to run across a million documents. But run over 50–100 BM25 candidates? Fast enough for real-time use. The heavy lifting is already done.

The default model is cross-encoder/ms-marco-MiniLM-L-6-v2 — fine-tuned on MS MARCO passage ranking, roughly 80 MB, runs comfortably on CPU.

reranker = CrossEncoderReranker(
    model_name="cross-encoder/ms-marco-MiniLM-L-6-v2",
    batch_size=32,
    max_length=512,
)
rag.warmup()  # pre-load at startup to avoid cold-start latency
ranked = reranker.rerank(query, candidates, top_k=5)

Module Deep-Dive: Query Expansion

Query expansion solves the single largest weakness of pure lexical search: vocabulary mismatch. If a user asks about "automobiles" and your documents only use "car," BM25 returns zero results and the Cross-Encoder never gets a chance to help.

GrepSearch ships two expander backends behind a common BaseExpander interface, selectable via a single config string.

WordNetExpander — Fully Offline

Uses NLTK's WordNet corpus to find synonyms for each word in the query. Instantaneous (~1ms), requires no API key, produces clean dictionary-validated synonyms.

# Offline — zero latency, no API key
config = PipelineConfig(
    use_query_expansion=True,
    query_expansion_backend="wordnet",
)

# "automobile engine problems" →
# ['automobile engine problems', 'car', 'vehicle', 'machine', 'motorcar']

LLMExpander — Richer Synonyms

For technical domains or multi-word phrases where WordNet falls short, LLMExpander calls any OpenAI-compatible API to generate alternative phrasings. Works with OpenAI, Ollama, LM Studio, or any compatible endpoint. If the API call fails or times out, it silently returns the original query — the pipeline never breaks.

# LLM-based (Ollama local)
config = PipelineConfig(
    use_query_expansion=True,
    query_expansion_backend="ollama",
    llm_base_url="http://localhost:11434/v1",
    llm_model="llama3",
)

# "connection pool exhaustion" →
# ['connection pool exhaustion', 'database pool depletion',
#  'max connections exceeded', 'pool timeout error']

Index Persistence

The BM25 index can be saved to disk and reloaded instantly, so your server doesn't need to re-chunk and re-index on every restart.

# Save
rag.save_index("my_index.pkl")

# Reload — no chunking or indexing needed
rag = GrepRAG.load_index("my_index.pkl", config=config)

When Should You Use This?

GrepSearch is not the right tool for every situation. Here's an honest assessment.

Use GrepSearch when…

  • Exact keyword matching matters (code, logs, IDs)
  • You don't want to manage a vector database
  • Your corpus fits in a few GB of disk
  • Building a local-first or offline application
  • Your domain has narrow, predictable vocabulary
  • You need near-zero infrastructure overhead

Stick with vector search when…

  • Your corpus is multilingual
  • Queries are highly abstract, keywords never appear
  • You're already operating a comfortable vector pipeline
  • Billions of vectors with sub-millisecond ANN
The hybrid approach The ideal production architecture for many applications is a hybrid: BM25 as one retrieval path and vector search as another, results fused with RRF. The two approaches are complementary, not mutually exclusive.

Installation

pip install greprag

# WordNet expansion (offline, no API key)
pip install "greprag[expand-wordnet]"

# LLM-based expansion (OpenAI / Ollama)
pip install "greprag[expand-llm]"

# Everything
pip install "greprag[all]"
Sometimes the best AI engineering decision is the one that involves less infrastructure.
